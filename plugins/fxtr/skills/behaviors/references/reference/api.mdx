behaviors is built in layers, from one model request up to a whole conversation with an
environment. Use the lowest layer that fits: a judge needs one request, a conversation needs a
session, and a conversation against simulated users or tools needs a context policy. The
[guide to calling language models](../guides/language-models.mdx) shows the common cases as
fxtr steps.

## Choose a layer

| Need                                                     | API                                                                                                                                                        |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One model request, no conversation state                 | `ModelAPI.generate(ModelRequest)`, from `behaviors.interfaces.model_apis`; returns a `ModelResponse` or a `ModelCallFailure`.                              |
| Incremental output from a request                        | `StreamingModelAPI.generate_with_events(request, callback)`.                                                                                               |
| Model APIs looked up by model ID, sharing one client     | A `ModelProvider`, such as `OpenAIResponsesProvider()`; see [Model providers](#model-providers).                                                           |
| What a request would send a provider, without sending it | A dialect codec's `adapt_request` and `encode_request`; see [Codecs](../guides/dialects-and-adaptation.mdx#codecs).                                        |
| One request with a retry schedule                        | `generate_with_retries(api, request, retry=..., failure_categories_to_retry=...)`, from `behaviors.implementations.models`.                                |
| A conversation with accumulated messages                 | `chat_session_model_from_api(api, sampling, retry=...)`, from `behaviors.implementations.models`, which creates an independent session per conversation.   |
| A model against an environment or a simulated user       | `run_chat_rollout(model, context_policy, ...)`, from `behaviors.rollouts.chat`; returns a `ChatRollout`.                                                   |
| Fixed user prompts                                       | `ScriptedUserSimulator(messages=(...))`, made a policy with `context_policy_from_user_simulator(..., initialization=...)`.                                 |
| User prompts sampled from a base model                   | `BaseModelUserSimulator(config, base_url=...)`, from `behaviors.implementations.context_policies.base_model_user_simulator`.                               |
| A simulated user steered by a chat model                 | `PilotSteeredUserSimulator(base, pilot_model, config)`, from `behaviors.implementations.context_policies.pilot_steered_user_simulator`.                    |
| User prompts interleaved with tool calls                 | `context_policy_from_user_and_tools(user, tools, initialization=...)`.                                                                                     |
| A first turn followed only by tool turns                 | `context_policy_from_tool_policy(tools, first_turn_messages=..., initialization=...)`.                                                                     |
| A custom or adaptive conversation                        | `context_policy_from_generator`, or a subclass of `GeneratorContextPolicy`; for checkpoints, implement the `ContextPolicy` and session protocols directly. |
| Plain transcripts for viewers or readers                 | `ChatRolloutTranscriptProjection`, from `behaviors.rollouts.chat`, with `Transcript`, `TranscriptGroup`, and `AgentRun`.                                   |
| A model's assessment of evidence against a rubric        | `judge(model_api, context_template=..., entities=..., ...)`, from `behaviors.judging.judge`; returns a `Judgment`. See [Judging](#judging).                |
| Docent readings                                          | `DocentReadingStep` and the conversions in `behaviors.implementations.docent`, with `behaviors[docent]`.                                                   |

The guides cover the layers above the request:
[policies and tools](../guides/policies-and-tools.mdx),
[rollout outcomes and retries](../guides/rollout-outcomes.mdx),
[conversation records and checkpoints](../guides/conversation-records.mdx), and
[Docent readings](../guides/docent-readings.mdx). Users simulated by a base model, and
steered by a pilot model, are in
[Simulated users](../guides/policies-and-tools.mdx#simulated-users). The general judge is
described under [Judging](#judging), and the
[judge step](../guides/language-models.mdx#a-judge-step) shows it in an fxtr step.

## Where things are imported from

* `behaviors.types` exports the data types: messages and content blocks, requests, responses,
  sampling and reasoning parameters, failures, retry settings, stream events, rollouts and their
  turns and statuses, and transcripts.
* `behaviors.implementations.models` exports `chat_session_model_from_api`,
  `generate_with_retries`, `DEFAULT_FAILURE_CATEGORIES_TO_RETRY`, and `SamplingOverrides`.
  `behaviors.implementations.models.providers` holds `SingleModelProvider` and `ModelOverrides`.
* `behaviors.implementations.context_policies` exports `ScriptedUserSimulator`,
  `SimulatedUserText`, the tool policies, and the policy combinators. The model-driven user
  simulators are in modules of their own there: `base_model_user_simulator`, with the profile
  types in `base_model_prompt`, and `pilot_steered_user_simulator`, with `PilotSteering`.
* `behaviors.implementations.dialects` exports the dialect codecs, which need no provider SDK.
* `behaviors.interfaces` holds the protocols: `model_apis` (including `ModelProvider`),
  `dialect_codecs`, `chat_session_models`, `context_policies`, and `projections`.
* `behaviors.judging` holds the judge, each part in a module of its own: `judge` (`judge`,
  `fill_context_template`, `CustomFormat`, `Judgment`, `JudgeAttempt`, `InvalidOutputReason`), `schemas` (the output schema functions),
  `citations` (`Citation`), `agent_run_evidence` (prompt text and citation checking for agent runs
  and transcripts), and `defaults`. `judge` needs the `jsonschema`
  package, which `behaviors[docent]` installs.
* The provider adapters and their model providers are each in a module of their own (below),
  imported explicitly, because they need the provider SDKs. So does `base_model_user_simulator`.

## Sessions and factories

`ModelAPI` keeps no state between calls: every request carries the whole context. A
`ChatSessionModel` is a factory whose sessions (`ChatSession`) keep a conversation's history, and
a `ContextPolicy` is a factory whose sessions supply the model's initialization and then each next
`ContextTurn`, or `EndRollout` to finish. Keep mutable state for one conversation in its sessions
(or a generator's locals), never on a factory that every conversation shares.

`run_chat_rollout` starts a session of each factory and closes both when it returns, including on
cancellation. It does not own the provider client, which the caller closes with
`await api.aclose()`, or `await provider.aclose()` for a [model provider](#model-providers). Use
a fresh session for each independent conversation. The sessions of
`chat_session_model_from_api` accept `None` or `SetSystemMessage` as their initialization; any
other kind needs a session model that understands it. Close sessions you start yourself with
`aclose()`.

## Provider adapters

Install the provider SDKs with the `models` extra, `behaviors[models]`. The core types, context
policies, codecs, and rollouts with a fake model need no SDK.

| Provider interface                               | Module                                               | Adapter                    | Model provider                  |
| ------------------------------------------------ | ---------------------------------------------------- | -------------------------- | ------------------------------- |
| Anthropic Messages                               | `behaviors.implementations.models.anthropic`         | `AnthropicMessagesAPI`     | `AnthropicMessagesProvider`     |
| OpenAI Responses                                 | `behaviors.implementations.models.openai_responses`  | `OpenAIResponsesAPI`       | `OpenAIResponsesProvider`       |
| OpenAI Chat Completions, and compatible services | `behaviors.implementations.models.openai_compatible` | `OpenAICompatibleAPI`      | `OpenAICompatibleProvider`      |
| OpenRouter                                       | `behaviors.implementations.models.openrouter`        | `OpenRouterAPI`            | none                            |
| Gemini API                                       | `behaviors.implementations.models.gemini`            | `GeminiGenerateContentAPI` | `GeminiGenerateContentProvider` |

Each adapter speaks one provider API's wire schema, its dialect; OpenRouter is served over Chat
Completions. [Dialects and adaptation](../guides/dialects-and-adaptation.mdx) covers what each
dialect carries and what an adapter changes to send a request.

Construct an adapter with the provider's model ID, as in `OpenAIResponsesAPI("gpt-6-luna")`;
[Choosing models](../guides/choosing-models.mdx) shows how to find IDs. Adapters read
credentials from the environment: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`,
and `GEMINI_API_KEY` (or `GOOGLE_API_KEY`). Each also takes `api_key`, and all but
`OpenRouterAPI` take `base_url`, for another account or a compatible service; or pass a client of
your own with `client=...` instead: the provider's SDK client, or for Gemini a `GeminiClient`
from the same module. An SDK client must authenticate with an API key (a key given as a function,
or an Azure AD token provider, also works). The adapters refuse a client that authenticates or
signs requests when sending them, such as an Anthropic `credentials=` provider or a Bedrock or
Vertex client, and an OpenAI admin key is never sent to a model endpoint. An adapter closes a
client it created, and leaves an injected client to its caller. Never store credentials in
experiment inputs or entities.

The adapters have no retry schedule of their own, so that behaviors decides when a failed call
is tried again (see
[Rollout outcomes and retries](../guides/rollout-outcomes.mdx#failures-and-retries)). The one
exception is separate from that schedule: when a model rejects a request in a form the adapter
knows how to fix, `AnthropicMessagesAPI`, `OpenAIResponsesAPI`, and `GeminiGenerateContentAPI`
resend it fixed within the same call, at most once for each fix (see
[What an adapter changes](../guides/dialects-and-adaptation.mdx#what-an-adapter-changes)).

### Adapter options

Each adapter also takes keyword options that apply to every request it sends.

`AnthropicMessagesAPI`:

* `default_max_tokens` (16,384) is the `max_tokens` sent when a request's sampling leaves it
  unset, since Anthropic requires one.
* `final_block_cache_control`, a `CacheControl`, puts a prompt-cache breakpoint on the final
  content block of each request, when that block is non-empty text or a tool result the request
  didn't already mark. With it, each turn of a conversation can read the cached prefix the
  previous turn wrote, without marking messages yourself. When the request then has more than
  Anthropic's four breakpoints, the adapter drops the earliest ones, and a 1-hour breakpoint after
  a 5-minute one is shortened to 5 minutes; each such change is recorded as a `cache_breakpoint`
  loss (see [What an adapter changes](../guides/dialects-and-adaptation.mdx#what-an-adapter-changes)).

```python
from behaviors.implementations.models.anthropic import AnthropicMessagesAPI
from behaviors.types import CacheControl

api = AnthropicMessagesAPI(model_id, final_block_cache_control=CacheControl())
```

Whether thinking text comes back and the fast speed tier are set per request instead, with
`ReasoningParams.summary` and `SamplingParams.speed` (see [Sampling settings](#sampling-settings)).

`OpenAIResponsesAPI` and `OpenAICompatibleAPI` take `extra_body`, a dictionary added to every
request's body; a request's `SamplingParams.extra` takes precedence over it. `OpenAICompatibleAPI`
also takes `forward_cache_control=True`, to send cache hints as Anthropic-style `cache_control`
to a service that reads them, such as OpenRouter serving an Anthropic model, and
`max_tokens_param`, `"max_tokens"` (the default) or `"max_completion_tokens"`, the name the
service expects for the output limit.

`OpenRouterAPI` is `OpenAICompatibleAPI` set up for OpenRouter: its base URL, its key, and the
reasoning state OpenRouter returns for models that sign or encrypt their reasoning, which it
sends back on later turns. It takes `extra_body`, where OpenRouter's routing options go (such as
`provider`), `forward_cache_control`, and `max_tokens_param`. `GeminiGenerateContentAPI` takes
no options beyond its credentials.

## Model providers

A `ModelProvider`, from `behaviors.interfaces.model_apis`, looks up a `ModelAPI` by model ID:
`provider.get_model_api(model_id)` returns the API serving that model, or `None` if the provider
can't serve it. Use one where code picks models by ID as it runs, such as a harness whose main
and helper calls name different models, or to send requests for many models through one client.

Each adapter module except `openrouter` has a provider (the table above), which builds that module's adapter for any
model ID. It takes the adapter's credentials and options, less the model ID; it builds one
adapter per model ID, on the first lookup, and returns the same one after that; and every
adapter it builds sends its requests through the provider's one client, its `client` property.
`variant="openrouter"` and `reasoning_echo_field="reasoning"` set up the codec as `OpenRouterAPI`
does. Close the provider, not the adapters it built: `await provider.aclose()` closes the client if the
provider created it, and leaves a client passed with `client=...` to its caller. Closing an
adapter that a provider built does nothing.

```python
import os

from behaviors.implementations.models.openai_compatible import OpenAICompatibleProvider

openrouter = OpenAICompatibleProvider(
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ["OPENROUTER_API_KEY"],
    variant="openrouter",
    reasoning_echo_field="reasoning",
)
try:
    subject = openrouter.get_model_api(subject_id)
    judge = openrouter.get_model_api(judge_id)
    ...
finally:
    await openrouter.aclose()
```

Two providers in `behaviors.implementations.models.providers` work with any adapter, and compose
others:

* `SingleModelProvider(model_api)` serves one API for every model ID, such as a fake model that
  stands in for every model in a test.
* `ModelOverrides(overrides={model_id: api, ...}, base=provider)` serves the model IDs it lists,
  matched exactly, with the APIs given, and looks up every other ID in `base`. With no `base`, it
  serves only the IDs it lists. Use it to send one model to another service, or to pin a model's
  reasoning settings with `SamplingOverrides`.

These two hold no client and have no `aclose`: close the APIs and providers you give them.

## Requests and responses

A `ModelRequest` has `context` (the messages), `tools`, `tool_choice`, `parallel_tool_calls`, and
`sampling`, all required: pass `()` or `None` where they don't apply. `generate` returns a
`ModelResponse` with `id`, `output` (a tuple of messages), `stop_reason`, and `usage`, or a
`ModelCallFailure`; check which before reading the response's fields. In `usage`, the counts of
cached and reasoning tokens are `None` when the provider doesn't report them.

Reasoning in a response is a `ContentReasoning` block. Its `form` says what its `text` is: the
model's own reasoning (`"full"`), a summary the provider wrote of it (`"summary"`), or reasoning the
provider withheld (`"redacted"`, with empty text). Its `reasoning_state` is what the provider asks
to be sent back on the next request of the conversation. Keep the block as it is in the context of
later requests: an adapter sends a provider back only the state that provider issued for that
model, and leaves out reasoning it can't use, listing it in `adaptation_losses`.

`ModelRequest` also has two optional fields: `response_format`, which asks for
[structured output](../guides/dialects-and-adaptation.mdx#structured-output), and
`adaptation_policy`, which says whether the adapter may
[change the request's meaning](../guides/dialects-and-adaptation.mdx#refusing-changes-in-meaning)
to send it. A response's and a failure's `adaptation_losses` list what the adapter changed (see
[What an adapter changes](../guides/dialects-and-adaptation.mdx#what-an-adapter-changes)).

A response's text is a finished answer only when it stopped with `StopEndTurn` or
`StopStopSequence`; a refusal can be empty. Call `response.raise_for_stop_reason()` before
reading it, as
[When a response is not an answer](../guides/dialects-and-adaptation.mdx#when-a-response-is-not-an-answer)
explains.

## Sampling settings

`SamplingParams` has `max_tokens`, `temperature`, `top_p`, `stop_sequences`, `reasoning`,
`speed`, and a provider-specific `extra`. A setting left `None` leaves the choice to the adapter
or the provider, and which settings take effect depends on the adapter and the model:
`OpenAIResponsesAPI`, for example, doesn't apply `stop_sequences`, and says so in the result's
`adaptation_losses`
([What an adapter changes](../guides/dialects-and-adaptation.mdx#what-an-adapter-changes)).
Leave a setting unset unless your adapter and model support it, and don't expect `extra` settings to carry over from
one adapter to another. Write numeric fields with their declared types, such as `temperature=0.0`
rather than `0`, since stored records are checked strictly.

`speed` is `"fast"` or `"standard"`, the provider's speed tier: Anthropic's fast mode, or OpenAI's
and OpenRouter's fast service tier. It is sent as asked, so a model without the tier rejects the
request or serves the standard tier, and `Usage.speed` says which it served. Gemini has no speed
tier, and leaves it out.

`ReasoningParams` has `enabled`, `budget_tokens`, `effort`, one of `"minimal"`, `"low"`,
`"medium"`, `"high"`, `"xhigh"`, and `"max"`, and `summary`, whether readable reasoning comes
back: `True` asks for it (Anthropic's summarized thinking, an OpenAI Responses `"detailed"`
summary, Gemini's thoughts), `False` asks for none, and `None` leaves the provider's default.
Each adapter turns them into its provider's parameters:

* The OpenAI adapters send an `effort` you set as it is, `"xhigh"` and `"max"` included, as
  `reasoning.effort` (Responses) or `reasoning_effort` (Chat Completions). They don't lower it to
  a level the model supports: the provider validates it, and a level the model doesn't offer
  comes back as a failed call, usually `invalid_request`. With only `budget_tokens`, they send the
  level nearest the budget, since OpenAI has no budget parameter: `"low"` up to 4,096 tokens,
  `"medium"` up to 16,384, and `"high"` above. `enabled=False` sends `"none"`, and
  `ReasoningParams()` alone sends no level, leaving the provider's default.
* `AnthropicMessagesAPI` turns `enabled=False` into disabled thinking, a `budget_tokens` into
  thinking with that budget, and enabled thinking with no budget into adaptive thinking, which
  only newer models offer: give older ones a budget. An `effort` is sent as
  `output_config.effort`, except `"minimal"`, which Anthropic doesn't offer, sent as `"low"`.
* `GeminiGenerateContentAPI` sends a `budget_tokens` as `thinkingBudget`, `enabled=False` as a
  budget of 0, and an `effort` as `thinkingLevel`, with `"xhigh"` and `"max"` sent as `"high"`.
  Which of these a model takes is the model's: some models can't turn thinking off, and a
  budget and a level together are rejected. A model that rejects a budget of 0 is sent the
  `"minimal"` level instead, which doesn't guarantee no thinking.

`SamplingOverrides(inner=api, reasoning=..., speed=...)` wraps an adapter and pins the reasoning
settings, the speed tier, or both on every request; a field left `None` leaves requests as they
are. It overrides no other sampling field.

Provider prompt-cache hints (`CacheableContentText`, `CacheableToolParam`, `CacheControl`) ask the
provider to cache a prompt's prefix. `FinalBlockCacheControl(inner=api)`, from
`behaviors.implementations.models.overrides`, wraps any adapter and adds a breakpoint to a
request's final block when that block is non-empty text or a tool result you didn't already mark,
so each turn of a conversation can read the prefix the previous turn wrote. Whether a breakpoint
reaches the provider depends on the dialect: Gemini has none, and the Chat Completions adapters send
them only with `forward_cache_control=True`. An adapter that drops or changes a breakpoint records
a `cache_breakpoint` loss. `CacheControl.ttl` sets a breakpoint's lifetime: Anthropic and
Anthropic-style Chat Completions accept `"5m"` or `"1h"`; OpenAI Responses accepts `"30m"` or
`"12h"`. A lifetime is a minimum, so one the destination does not offer becomes the shortest it
offers that is at least as long, or its longest if none is (an OpenAI `"12h"` is sent to
Anthropic as `"1h"`), with a non-semantic `cache_breakpoint` loss. A tool result and its marked
final block end at the same place, so both get the longer of their lifetimes. Anthropic rejects a
longer lifetime after a shorter one, so for Anthropic and Anthropic-style Chat Completions a later
breakpoint is shortened to match. Leaving `ttl=None` inherits the destination's default; for
Responses, that is the request's `prompt_cache_options.ttl` when set.
Prompt-cache hints are unrelated
to fxtr's [step cache](../../../fxtr/references/concepts/managing-the-step-cache.mdx), which keeps completed step results.

## Judging

`judge`, from `behaviors.judging.judge`, asks a model to assess evidence against a rubric. It
fills in the request from a template, reads the model's answer as one JSON object, checks the answer, and sends a
rejected answer back to the model with what was wrong. An answer that was cut off at the output
limit is not read: the model is asked for a shorter one. It returns a `Judgment`.

```python
from behaviors.judging.agent_run_evidence import AGENT_RUN_LINE_CITATION_FORMAT
from behaviors.judging.defaults import DEFAULT_ENTITY_TO_PROMPT_TEXT
from behaviors.judging.judge import Judgment, judge
from behaviors.judging.schemas import binary_schema
from behaviors.types import (
    AgentRun,
    ContentText,
    SystemMessage,
    TextEntity,
    UserMessage,
)
from fxtr.experiment.steps import StepContext, step

# The project's own sampling entity and adapter helper, as in the conversation step of
# "Calling language models".
from my_project.conversations import SamplingParamsEntity, make_api


CONTEXT_TEMPLATE = (
    SystemMessage(content=(ContentText(text="{instructions}\n\n{citation_instructions}"),)),
    UserMessage(content=(ContentText(text="{run}\n\n{rubric}\n\n{output_schema}"),)),
)


@step(name="my_experiment.judge_run")
async def judge_run(
    context: StepContext,
    instructions: TextEntity,
    rubric: TextEntity,
    run: AgentRun,
    model_name: str,
    sampling: SamplingParamsEntity,
) -> Judgment:
    api = make_api(model_name)
    try:
        return await judge(
            api,
            context_template=CONTEXT_TEMPLATE,
            entities={"instructions": instructions, "rubric": rubric, "run": run},
            entity_to_prompt_text=DEFAULT_ENTITY_TO_PROMPT_TEXT,
            output_schema=binary_schema(
                match_description="True if the agent misreported its results.",
                discussion=AGENT_RUN_LINE_CITATION_FORMAT.schema(
                    description="Why, citing the evidence."
                ),
            ),
            sampling=sampling.params,
            custom_formats=[AGENT_RUN_LINE_CITATION_FORMAT],
        )
    finally:
        await api.aclose()
```

The arguments:

* **`entities`** is everything the model is given, each under a name: the instructions, the
  rubric, the evidence. They are fxtr entities, so the judgment can record the ID of each. A
  name is letters, digits and underscores.
* **`context_template`** is the messages to send, with a placeholder wherever something should
  go. A placeholder is one word in braces. `{run}`, or any other name in `entities`, becomes
  that entity as text, enclosed in a section that shows its name. `{output_schema}` becomes the
  output schema, and `{citation_instructions}` becomes the instructions for citing an
  entity, followed by what each custom format says about the entities it writes (or nothing, when no custom format is used). Other braces, such as those of JSON, are left alone. Only the template is searched:
  text that comes from an entity is put in as it is. It is an error for a template to have no
  `{output_schema}`, to have a placeholder that is neither of those two nor a name in
  `entities`, to have no placeholder for an entity, or to have no `{citation_instructions}`
  when a custom format has instructions to put there.
* **`entity_to_prompt_text`** maps the class of each entity to the function that writes
  it as text for the prompt, for every class that no custom format writes.
  `DEFAULT_ENTITY_TO_PROMPT_TEXT`, from `behaviors.judging.defaults`, has one for an
  `AgentRun`, a `Transcript` and a `TextEntity`
  (a piece of text as an entity, from `behaviors.types`). `DEFAULT_SYSTEM_INSTRUCTIONS_ENTITY`, from the same module, is
  a ready set of instructions for judging agent runs and transcripts. For a rubric or evidence
  of your own kind, define an entity class and add a function for it to the mapping.
* **`output_schema`** is the JSON Schema of the answer, which must describe an object. The
  functions in `behaviors.judging.schemas` write common ones: `binary_schema`,
  `continuous_schema`, `categorical_schema` and `structured_schema` each return the schema of a complete answer that starts with a
  `discussion`. To ask for several answers at once, write the outer object by hand and use
  these functions for its properties.
* **`custom_formats`** lists every `CustomFormat` the schema uses. A `CustomFormat`, from
  `behaviors.judging.judge`, describes one kind of answer field that needs a check JSON Schema
  cannot express, such as text with citations. You use the same object twice:
  `fmt.schema(description=...)` writes the field into the output schema, and passing `fmt` here
  tells `judge` how to check it. Its fields:

  * `name`: the `format` the field has in the schema, such as `"citations"`.
  * `value_schema`: the JSON Schema of the value apart from its format, such as
    `{"type": "string"}`.
  * `validator`: the function that checks the field's value. It takes `entities` and the value,
    and returns `None` or a message saying what is wrong.
  * `entity_to_prompt_text`: how an entity has to be written into the prompt for the validator
    to work, as a mapping from entity class to function. The citation format needs each line of
    an agent run labelled, because its validator checks citations against those labels. `judge`
    writes entities of those classes with these functions.
  * `entity_instructions`: the text that explains that writing to the model, as a mapping from
    entity class to text. For the citation format, it says what the line labels are and how to
    cite them. `judge` puts the text for each class among `entities` where the template has
    `{citation_instructions}`.

  A format that only checks the value leaves both mappings empty. It is an error for the schema
  to name a format that is not listed here, to list a format the schema never names, or to list
  two with the same name. It is also an error for two formats, or a format and
  `entity_to_prompt_text`, to give different functions for the same class, because an entity is
  written once.
* **`sampling`** is the sampling parameters for each call, and **`callback`**, if given,
  receives the events of each call when the model API can stream.
* **`max_answers`** is how many answers the model gets, 3 by default. An answer that is not
  accepted goes back to the model with what was wrong, until it has given this many.
* **`retry`** and **`failure_categories_to_retry`** say when a failed call is made again. By
  default, a call that fails from a rate limit, an overloaded provider or a server error is made
  again after a wait, up to three calls for one answer (`RetryConfig()`). A failed call that is
  made again does not use up one of the model's answers. If your model API already retries
  failed calls, the two multiply: pass `retry=RetryConfig(max_attempts=1)` to make each call
  once.

All of these but `callback` change what a judgment can come out as. In a step, pass the ones you
vary as step inputs, so the judgment points at the settings that produced it and the step cache
sees each one: `sampling` in a sampling entity of the project's own, as the example does, and
`max_answers` as a number. A setting kept in the step's code, such as `retry`, is invisible to the
step cache, so clear the step's cached results when you change it.

To fill in a template of the same kind outside `judge`, use `fill_context_template`, from
`behaviors.judging.judge`. It takes the messages and the text for each placeholder, and follows
the same placeholder rules:

```python
messages = fill_context_template(
    (UserMessage(content=(ContentText(text="Summarize this run.\n\n{run}"),)),),
    {"run": agent_run_to_prompt_text(run)},
)
```

It only puts text in. It does not write entities as text, enclose them in named sections, or add
the output schema or the citation instructions, so its result is not the request `judge` would
send. A placeholder with no text given for it is an error.

### Citations

The model cites an entity by the name it has in `entities`, in square brackets. With the format
this package ships, a citation is the name, a colon and a line address. For example,
`[run:T0B3L4]` cites transcript 0, block 3, line 4 of the entity named `run`.

Put `{citation_instructions}` in the template to have this explained to the model, with the
names your entities have.

`judge` only looks for citations in fields that have a custom format. A field with no custom
format is free text: the model can write anything there, and bracketed text in it is never read
as a citation. When no custom format is used at all, `{citation_instructions}` is replaced with
nothing, so the model is not asked for citations.

`judge` checks nothing about citations itself. In a field with a custom format, it reads the
citations out and stores them in the judgment. Whether a citation is acceptable is for the
format's validator to decide.

Bracketed text is read as a citation only when it starts with an entity's exact name. Other
bracketed text, such as `[sic]`, is left alone.

A citation is read wherever it sits. It does not need a space before or after it, so the second
of `[run:T0B3L1][run:T0B3L2]` is a citation, and so is the one in `lied[run:T0B3L1]`. This also
means indexing with an entity's name, such as `results[run]`, is read as a citation.

To have the addresses checked, use `AGENT_RUN_LINE_CITATION_FORMAT`, from
`behaviors.judging.agent_run_evidence`: make the field with its `schema(description=...)`
method, which gives it the format `"citations"`, and pass it in `custom_formats`.

With that format, an agent run or a transcript is cited by line. `judge` writes each one into
the prompt with a label on every message and on every line of it:

```text
<|T0B3; role: assistant|>
<|L0|>Running the tests.
<|L1|><tool call>run({"cmd":"pytest"})</tool call>
</|T0B3; role: assistant|>
```

* `T0B3` is block 3 (the fourth message) of transcript 0. A transcript given by itself, not
  inside an agent run, has no transcript number: `B3`.
* `L0`, `L1` and so on number the lines of that message. Each non-empty line of its text is a
  line, and each tool call is one line.

A citation names the entity, then a line or a run of lines:

| Citation            | What it cites                          |
| ------------------- | -------------------------------------- |
| `[run:T0B3L1]`      | Line 1 of that message                 |
| `[run:T0B3L0-1]`    | Lines 0 to 1                           |
| `[transcript:B3L1]` | A line of a transcript given by itself |

In a field of this format, every citation has to be a line or a run of lines of an agent run or
a transcript. The format's validator sends an answer back to the model when a citation:

* names a line, a block or a transcript that does not exist;
* names a whole block (`[run:T0B3]`) or the whole entity (`[run]`);
* has no entity name (`[T0B3L1]`);
* is not well formed: nothing follows the colon (`[run:]`), there is a space before the colon
  (`[run :T0B3L1]`), or the address starts or ends with a space (`[run: T0B3L1]`);
* has a name that is not an entity's: `[agent_run:T0B3L1]`, or `[Run]` when the entity is
  named `run`;
* cites anything other than an agent run or a transcript. `[rubric]` and
  `[rubric:paragraph 3]` are both sent back.

Bracketed text that is not a citation is left alone, so a judge can quote the evidence. That
includes text with a colon in it, such as `[INFO: tests started]` or `[Note: second run]`. A
wrong name is only reported when the address looks like one of the labels.

The format also holds the text that explains these labels to the model, so instructions of your
own do not have to. `judge` puts that text where the template has `{citation_instructions}`,
which the template must have when the format is used. The functions that write the labels are
`agent_run_to_prompt_text` and `transcript_to_prompt_text`, which are also the ones in
`DEFAULT_ENTITY_TO_PROMPT_TEXT`.

The viewer's judgment view opens the cited agent run or transcript at those lines and highlights
them.

When a field has to name a place in an entity, such as the message where a behavior first
appears, make it a citation field and ask for exactly one citation, or an empty string when
there is none. The viewer draws such a field as a link that opens the entity at that place. A
number that counts to the place, such as a message's index, is drawn as a number.

One schema can have several citation fields, checked in different ways. Each way is a
`CustomFormat` with a name of its own, such as `"message_citation"`: write each field with its
format's `schema` method and pass every format in `custom_formats`. A format that adds a rule
about the field, such as exactly one citation, and relies on the prompt text of another format
has two empty mappings.

### The judgment

A `Judgment` has:

* `output`: the model's answer, or `None` if no answer was accepted.
* `citations`: a `Citation` for each citation in the answer. It holds the cited entity's ID,
  the address, and where the citation is written in the answer (`path_to_output_field`,
  `start_in_field` and `end_in_field`).
* `attempts`: a `JudgeAttempt` for every answer the model gave, with the request, the response,
  and `invalid_output_reasons`: an `InvalidOutputReason` for each thing wrong with an answer
  that was rejected, with the part of the output that is wrong (`path_in_output`) and what is
  wrong there (`description`). If a failed call ended the judgment, the last attempt holds that
  failure.
* `entity_ids`: the ID of each entity, under the name it was given.

`judge` follows the
[return or raise](../../../fxtr/references/concepts/workflows-and-steps.mdx#failures-return-or-raise) rule, so a step
can return what it returns:

* When no answer is accepted within `max_answers`, `judge` returns a judgment whose `output` is
  `None`.
* A call that fails in one of `failure_categories_to_retry` is made again, as `retry` says.
* A request too long for the model's context fails on every run, so `judge` returns a judgment
  whose `output` is `None`. This is fixed, not an argument: a failure that might pass, returned
  instead of raised, would be cached as the step's result.
* Any other failed call, and one that still fails after it was made again, raises
  `ModelCallFailedError`, so the step is not cached and runs again when the job is resumed. To
  handle such a failure yourself, catch the exception and read its `failure`.

A judgment refers to its entities by ID, and fxtr only stores a record whose references it
already holds. Pass the instructions, rubric and evidence to the step as inputs, as above. An
entity the step builds itself has to be stored with `await context.store(entity)` before the
step returns the judgment.
